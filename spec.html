§1

项目概述

品牌信息
  • 品牌名（产品名）： KnosAI
  • 中文产品名： 企业知识绿洲
  • 域名 / 公司主体： knosAI.ltd
  • 项目类型： 行业知识库平台 Landing Page
  • 行业定位： 先做环保行业（污水处理站运维托管），后续按行业扩展
  • 目标用户： 环保、医疗、制造、餐饮等行业的中小型企业（B 端）

核心价值主张

不是问答工具，是企业专属知识库平台。

通过引导式问答 + 文档上传，自动构建贴合企业自身的完整知识库，让员工和客户随时可问、可查、可用。

行业扩展策略

当前（v1）：环保行业 - 污水处理站运维 → 未来扩展：环保 → 制造 → 医疗 → 餐饮 ... ↓ 每个行业独立的基础知识库 + 独立引导模板 + 独立文档适配器 系统设计时预留行业扩展接口，新增行业不改主代码，只需新增行业包。
§2

核心产品架构

2.1 三层知识结构

┌────────────────────────────────────────────────────┐ │ 企业知识库（用户最终看到的） │ │ │ │ = 行业基础知识库（隐性） │ │ + 引导式问答获取的知识 │ │ + 用户上传的知识库文档解析后的知识 │ │ │ │ 用户视角：这就是"我公司的知识库" │ └────────────────────────────────────────────────────┘ ↑ ↑ ↑ 隐性基础库 引导式问答 文档上传 （平台预置） （挖隐性） （整显性）
关键原则
  • 行业基础知识库是隐性的——用户感知不到"这是平台预置的"，他只看到"我的企业知识库"
  • 用户体验上，企业知识库 = 一个完整、统一的知识库，不区分来源
  • 三个数据源在底层有来源标记（用于后续分析、审计、去重），但呈现层透明

2.2 三条知识获取路径

路径适用场景用户操作数据流向
路径 A引导式问答没文档、有经验的老师傅系统提问 20-30 个 → 用户回答入企业库
路径 B 文档上传有现成文档的企业上传 PDF/Word/Excel/MD/TXT解析入企业库
路径 C 行业基础库（隐性）所有用户首次进入无需操作，自动初始化隐性注入

2.3 用户视角的"五步上手"（v2.2 多站点版）

① 选择行业（环保-污水处理站运维） ↓ ② 填写公司信息 + 确认托管站点数量 ↓ ③ 逐站引导问答（每个站点独立获取，达成目标即结束） └─ 目标导向，不限题数 ↓ ④ 上传文档（可选，可按站点分类上传） ↓ ⑤ 企业知识库可用 ├─ 公司层：通用信息 + 站点清单 ├─ 站点层：每个站点独立知识模块 └─ AI 问答：支持按站点检索
§3

行业基础知识库设计（隐性层）

3.1 为什么需要"行业基础库"

环保行业污水处理站的标准工艺、法规、设备是通用的，如果让每家企业都从零录入：重复劳动 / 信息不专业 / 上手门槛高。所以平台预置行业基础知识库，作为隐性底座。

3.2 行业基础库内容结构（环保-污水处理站运维 示例）

行业基础库（隐性注入）: 法规标准: - 医疗机构水污染物排放标准 GB18466-2005 - 城镇污水处理厂污染物排放标准 GB18918-2002 - 污水综合排放标准 GB8978-1996 工艺流程: - 预处理 → 一级处理 → 二级处理 → 深度处理 → 消毒 - 常见工艺：A²O、SBR、MBR、MBBR 通用设备: - 格栅、潜水泵、鼓风机、曝气头、污泥泵、加药装置 常见异常: - 泡沫、污泥膨胀、出水超标、设备故障 运维要点: - 巡检要点、药剂投加、污泥处理、应急预案

3.3 行业扩展接口设计

industries/ ├── env-water-station/ # 环保-污水处理站（首期） │ ├──base-knowledge.yaml 行业基础知识库 │ ├── qa-template.yaml 引导问答模板（20-30 题） │ ├── doc-parser-rules.yaml 文档解析规则 │ └── vocabulary.yaml 行业术语表 ├── env-waste-gas/ # 环保-废气处理（未来） ├── manufacturing/ # 制造业（未来） └── ... 加新行业的成本：新建一个行业包目录，无需改主代码。

3.4 行业基础库的动态更新机制（v2.1 重要原则）

核心原则

基础包不是静态的，企业越多，基础包越完善。

企业使用过程 ┌──────────┐ │引导问答 │ │ 文档上传 │ └─────┬────┘ ↓ ┌──────────────────────┐ │ 企业知识库（私有） │ └──────────┬───────────┘ │ 脱敏 + 抽象化 + 聚合 ↓ ┌──────────────────────┐ │ 行业基础库（共享） │ ← 持续进化 │ · 新发现的最佳实践 │ │ · 新出现的异常类型 │ │ · 新法规/新标准 │ │ · 高频问答沉淀 │ └──────────┬───────────┘ ↓ ┌──────────────────────┐ │ 所有新企业受益 │ └──────────────────────┘
数据类型来源抽象化处理入基础库
引导问答中的老师傅经验多家企业去标识化、归纳为通用实践行业最佳实践库
文档中的企业专属 SOP多家企业脱敏、提取通用部分行业操作规范库
真实异常处理案例多家企业去除企业信息，保留通用模式行业异常案例库
用户高频提问多家企业统计 + 归类行业 FAQ 库
法规标准更新平台维护人工/AI 抓取行业法规库
动态更新触发机制
  • 同一类问题在 ≥ N 家企业被问到
  • 新的法规/标准发布
  • 新的设备/工艺类型出现
  • 平台运营人员审核通过
对企业的价值主张（落地页表达）

"您贡献的经验，会让整个行业知识库更完善 —— 而完善的行业基础库，又会反过来服务您的企业。这是一个越用越聪明的正循环。"

§4

路径 A · 引导式问答详细设计

4.1 设计目标

让老师傅"不用写文档，打开就问"，把脑子里的经验挖出来。

4.2 设计原则：目标导向，不限数量 v2.2 重要更新

核心原则
  • ❌ 不设固定问题数量（"20-30题"只是参考范围）
  • ✅ 设目标体系：明确"我们需要什么信息"
  • 预设问题库作为工具库，实际问答根据目标动态调整
问答设计逻辑 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 目标：获取企业知识库所需的完整信息 ↓ 预设问题库（工具箱，不等于必须全问完） ├─ 工艺类问题（15个） ├─ 参数类问题（12个） ├─ 异常处理类（10个） └─ ... ↓ 实际问答流程 ├─ 系统判断"当前站点还需要什么" ├─ 动态选下一题（不是线性顺序） └─ 目标达成即结束 （可能15题，可能35题，取决于站点复杂度） ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.3 多站点场景 v2.2 重要更新

真实业务逻辑

大多数污水站运维公司不只托管一个站。一家运维公司同时托管 N 个污水站，每个站情况都不同。

企业知识库结构 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │ 公司层 │ ├── 公司基本信息（名称/规模/资质） │ ├── 托管站点清单（站点A/B/C...） │ ├── 运营管理模式（集中值守/分散巡检/远程） │ └── 跨站点通用 SOP │ │ 站点 A（独立知识单元） │ ├── 基础信息（工艺/水量/水质/设备） │ ├── 运营参数（DO/SV30/pH/加药量） │ ├── 异常处理（泡沫/污泥膨胀/出水超标） │ └── 应急预案（停电/设备故障/达标风险） │ │ 站点 B（同上结构，内容独立） │ └── ... │ │ 站点 C... │ │ + 行业基础库（隐性） ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.4 问答目标体系（三层）v2.2 新增

层级目标说明
公司层公司基本信息名称、规模、资质
托管站点清单一共托管几个站，站点名称和位置
运营管理模式集中值守 / 分散巡检 / 远程监控
人员配置多少人，怎么分工
通用 SOP跨站点的统一管理制度
站点层站点基本信息站点名、服务客户、日处理水量
工艺流程一级/二级/深度处理各单元
进水水质COD/BOD/氨氮/SS/TN/TP 范围
出水标准执行哪个标准（GB18466等）
设备配置主要设备清单、规格参数
关键控制参数DO/SV30/pH/回流比/加药量
日常巡检要点每天/每周/每月巡检内容
常见异常处理泡沫/污泥膨胀/出水超标等
应急预案停电/设备故障/水质超标
补充层老师傅经验"我们站遇到XX情况的处理方法"
企业特色做法同行没有的、本站特有的经验
近期待解决问题目前有什么棘手问题

4.5 问答流程（多站点版）

① 收集公司基本信息 ↓ ② 确认托管站点数量 → 获取各站点名称/位置/规模 ↓ ③ 逐站引导问答（每个站点独立一套目标） ├─ 站点 A：引导问答（目标达成）→ 生成站点知识模块 ├─ 站点 B：引导问答（目标达成）→ 生成站点知识模块 └─ 站点 C... ↓ ④ 公司层信息汇总 + 各站点知识模块合并 ↓ ⑤ 企业知识库完成 （公司层 + N个站点模块 + 行业基础库）

4.6 预设问题示例（环保-污水处理站） v2.2 新增

公司层问题
  • Q1: 公司名称和成立时间？
  • Q2: 目前托管了多少个污水站？能否列出站点名称和位置？
  • Q3: 这些站点的服务客户类型有哪些？（医院/小区/工业园/其他）
  • Q4: 公司有多少名运维人员？怎么分工的？
  • Q5: 有没有跨站点的统一管理制度？
站点层问题（每个站点重复）
  • Q6: 这个站点的名称和处理规模（日处理量 m³/d）？
  • Q7: 服务的是哪类客户？进水水质大概什么范围？
  • Q8: 用的是哪种工艺？每个处理单元的作用是什么？
  • Q9: 出水执行哪个排放标准？（GB18466 / GB18918）
  • Q10: 主要设备有哪些？规格参数？
  • Q11: 曝气池溶解氧一般控制在多少？
  • Q12: 出现污泥膨胀时怎么处理？
  • Q13: 出水超标时的应急处置流程？
  • ...（以上只是示例，预设问题库按目标体系扩展，不强制全问）

4.7 用户体验设计（产品内部）

  • 首页：公司层信息收集（简短，5-10题）
  • 次页：站点选择（已有站点列表 + 新增站点）
  • 逐站问答：每个站点独立引导，目标达成后进入下一站
  • 进度展示："已完成 2/5 个站点，共采集 38 条知识"
  • 退出提示："您的企业知识库已包含 3 个站点的完整信息，随时可保存退出"
Landing Page 展示方式

用户旅程模块展示多站点问答流程，强调目标导向：把该挖的都挖到，不漏关键信息。

5.1 设计目标

让"已经有文档的企业"快速整合资料，无需重复录入。

5.2 支持的文档类型

类型格式优先级备注
Word 文档.doc / .docx⭐⭐⭐⭐⭐最常见，含图/表/格式
PDF 文档.pdf⭐⭐⭐⭐⭐扫描件需 OCR
Excel 表格.xls / .xlsx⭐⭐⭐⭐数据/参数表
Markdown.md⭐⭐⭐技术文档常见
纯文本.txt⭐⭐简单备查

建议按以下结构组织文档，效果最好（不强求）
📁 公司文档/ ├── 01_公司简介.md （公司背景、规模、资质） ├── 02_工艺流程/ │ ├── 工艺总览.md │ ├── 预处理单元.md │ ├── 生化处理单元.md │ └── 消毒排放.md ├── 03_设备手册/ │ ├── 设备清单.xlsx │ ├── 鼓风机操作.md │ └── 加药系统维护.md ├── 04_运维制度/ │ ├── 巡检制度.md │ ├── 交接班制度.md │ └── 药剂管理制度.md ├── 05_应急预案/ │ ├── 停电应急.md │ ├── 设备故障.md │ └── 出水超标.md └── 06_常见问题FAQ.md

5.4 上传后处理流程

用户上传文档 ↓ 格式识别 + 解析（PDF/Word/Excel 各自适配器） ↓ 章节切分（识别标题层级） ↓ 关键信息抽取（参数、术语、操作步骤） ↓ 与行业基础库比对（识别"通用部分"和"企业特色部分"） ↓ 合并入企业知识库（打来源标签） ↓ 生成结构化目录 + 摘要
